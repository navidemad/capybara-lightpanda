# What would it take to switch a Cuprite suite to Lightpanda?

A suite that uses the Capybara DSL for forms, DOM assertions and navigation can try Lightpanda today by changing its driver registration. The first compatibility work should target **suite setup and shared helpers**. A copied remote-browser option can silently launch a local process. A cookie helper that succeeds on Cuprite can fail before the first assertion. A modified click or an unwrapped confirm can execute the opposite application branch while the test continues.

**Audit baseline, 18 November 2026.** The comparison uses the published Cuprite 0.20.1 and Ferrum 0.20.1 gems, Capybara 3.40.0, and capybara-lightpanda main at `1c93471` with browser 1.0.4. The gem on main reports 0.19.1 but includes changes after that release, notably `driver.user_agent=`. Cuprite 0.20 deprecated many `page.driver` helpers in favor of `page.driver.browser`. Both surfaces matter to migrants. [Cuprite release and deprecations](https://github.com/rubycdp/cuprite/blob/v0.20.1/CHANGELOG.md) · [Ferrum browser interface](https://github.com/rubycdp/ferrum/blob/v0.20.1/lib/ferrum/browser.rb) · [Lightpanda changes since 0.19.1](https://github.com/navidemad/capybara-lightpanda/compare/v0.19.1...1c93471)

## What a migrating suite can observe

I ran the same Rack page in separate processes with Cuprite on Chrome for Testing 156.0.8078.4 and with Lightpanda on 1.0.4. The page had a labeled input, a button that displayed the click event’s `shiftKey`, a paragraph echoing a request header, and, for the download probe, a link to a CSV attachment. In the table, `b` is `page.driver.browser`. Each row records an observed result from that fixture.

| Call or assertion | Cuprite | Lightpanda |
| --- | --- | --- |
| Visit, read title, fill a labeled input and read its value | Returned `"Audit"` and `"Ada"` | Same |
| `b.headers.set("X-Audit" => "present")`, then revisit | Server received the header | `NoMethodError` on `headers`. The existing spelling is `page.driver.headers = {...}` |
| `b.cookies.set(name: "audit", value: "yes")` after visiting | Returned true | `BrowserError` requiring a domain or URL |
| Set the cookie with explicit domain, then `b.cookies["audit"].value` | `"yes"` | `"yes"` |
| `b.cookies.all` | Hash keyed by name | Array of cookie objects |
| `b.network.traffic.first` after navigation | Exchange object with `request` and `response` | Hash with symbol keys |
| `b.network.clear(:traffic)` / `wait_for_idle(duration: 0.01)` on the network object | Cleared traffic / returned true | Both raised `ArgumentError`. Current forms are `clear` and `wait_for_idle(timeout:, connections:)` |
| `b.downloads.wait { page.click_link("Report") }` | Ran the block, wrote the CSV, recorded a metadata hash | Returned without calling the block or writing a file |
| `find("button").click(:shift)` | Handler read `true` | Handler read `false` |
| Evaluate an unwrapped `confirm("Continue?")` | Warned and returned `true` | Warned and returned `false` |
| Callback after 1 s, Capybara wait 0.5 s, driver timeout 3 s | Raised `Ferrum::ScriptTimeoutError` | Returned the callback value |

The rest of the audit follows the released sources and this repository’s implementation and fixtures. The Forem integration is a useful migration example. Its patch replaces a named Cuprite registration, including optional remote Chrome discovery, with the stock Lightpanda registration. A passing patched spec would exercise its application flow while bypassing the original initializer. ## 1. Make switching drivers explicit and predictable

Today the gem registers `:lightpanda` and uses `Capybara::Lightpanda::Driver`. A team can keep its application-owned registration name and its specs by changing the initializer. For example, this preserves Forem’s `driven_by :better_cuprite` locally. Set `ws_url:` explicitly to a **Lightpanda** WebSocket endpoint when running remotely. Suites on Ruby 3.2 also need a Ruby upgrade. Both peer gems support 3.2, while this gem requires 3.3 or newer. [Registration](lib/capybara-lightpanda.rb) · [Gemspec](capybara-lightpanda.gemspec)

```ruby
require "capybara-lightpanda"

Capybara.register_driver(:better_cuprite) do |app|
  Capybara::Lightpanda::Driver.new(app, window_size: [1200, 800], timeout: 15)
end
```

| Copied Cuprite configuration | Current outcome and proposed treatment |
| --- | --- |
| `window_size`, `timeout`, `process_timeout`, `save_path` | Recognized. Pin dimensions and timeouts when migrating. Ferrum defaults to 1024×768 and a 5 s timeout, Lightpanda to 1920×1080 and 15 s absent environment overrides. Resizing changes the JS viewport. Resize before visiting when asserting stylesheet media queries. |
| `url:`, `ws_url:`, `browser_path:` | Only an explicit `ws_url:` selects remote mode here. A copied HTTP `url:` is ignored and a local browser can start. A Chrome executable is also the wrong binary for `browser_path:`. Diagnose `url:` before launch with the expected endpoint format. Test the remote branch with local spawning forbidden. |
| `extensions:`, `js_errors:`, `pending_connection_errors:` | Ignored. Missing setup scripts or error policies can change test outcomes silently. Support extension paths and `{source: ...}`, define ordering against the injected bundle, and exercise first navigation, child frame and reset. Until implemented, report requested policies explicitly. `browser.page_errors` can already be asserted in teardown. |
| `raise_on_unhandled_modal:`, `headless:`, `inspector:` | The modal option exists, but the default confirm result differs. Use explicit Capybara dialog blocks for branch-sensitive tests. `headless: false` cannot open a UI and `inspector:` is ignored. `driver.pause` pauses Ruby, whereas Cuprite’s `debug(binding)` supports interactive inspection. |
| `screen_size:`, `emulate:`, `mobile:`, `scale_factor:`, `browser_options:`, `dockerize:`, `proxy:` | None are interpreted as Cuprite configuration. A viewport covers some responsive tests. It cannot supply device touch, pixel density, Chrome flags, or proxy routing. Diagnose nonempty behavioral settings, including proxy use, before any request. |

**First deliverable (small).** Publish this registration recipe and an opt-in Cuprite option checker with a useful message per unsupported setting. Keep both gems loadable together and test both require orders. Global replacement of `require "capybara/cuprite"`, `Capybara::Cuprite`, or the stock `:cuprite` registration would take away the Chrome fallback from mixed suites. [Lightpanda options](lib/capybara/lightpanda/options.rb) · [Connection and script setup](lib/capybara/lightpanda/browser.rb) · [Ferrum options](https://github.com/rubycdp/ferrum/blob/v0.20.1/lib/ferrum/browser/options.rb)

## 2. Implement the helpers that break whole spec files

| Priority / effort | Change | Acceptance example |
| --- | --- | --- |
| First / small for ordinary headers | Add a `browser.headers` adapter over the existing network header state. Implement `get`, `set`, `add` and `clear`. Cover legacy `driver.add_header` separately. Ferrum handles a temporary Referer specially, and synchronizes navigator overrides for User-Agent and Accept-Language. | Have the **server** echo two ordinary headers. Verify replacement, merge, clear and reset. Check Referer on the next navigation, and compare an allowed user agent on the wire and in JS before promising those cases. |
| First / medium | Give browser-level cookie writes the visited host or configured base URL. Accept Ferrum’s positional options hash and `httponly` / `samesite` keys. Offer a Cuprite-facing name-keyed view of `all` while preserving native array callers and enumeration of same-name cookies at different paths. | Seed a login before the first visit with an app host, repeat after navigation, read via `cookies.all.fetch("session").value`, remove the scoped cookie, and verify a sibling path and the next example’s session. |
| First / medium | Give Cuprite callers a network view with `exchange.request.url`, `exchange.response.status`, main-document `network.status` / `response`, and `clear(:traffic)`. Keep hash access for existing users. Treat `clear(:cache)` as a separate operation. Provide `duration:` on idle waits and verify what “finished” means. Lightpanda closes ordinary pending entries on response headers. Ferrum considers response loading in `finished?`. | Exercise a redirect, a failed request and a delayed response body. Assert the returned objects, final status, idle timing, and that clearing recorded traffic leaves cache behavior alone. Include iframe traffic so it cannot overwrite the top-level status. |
| First / small for the trigger | Support the Cuprite idiom `browser.downloads.wait { click_link(...) }`. Ferrum yields to the trigger and exposes metadata hashes via `files`. Lightpanda accepts a keyword timeout, never yields, and returns absolute paths. Today a block-only call can finish without clicking anything. | Trigger exactly one attachment download inside the block. Verify its filename and bytes on disk and preserve the existing click-then-wait API. [Ferrum downloads](https://github.com/rubycdp/ferrum/blob/v0.20.1/lib/ferrum/downloads.rb) · [Lightpanda downloads](lib/capybara/lightpanda/downloads.rb) |
| Next / medium | Match the session wait for `evaluate_async_script` and distinguish a missing callback from a broken CDP connection. Give the transport enough time to deliver the script deadline. Implement a distinct navigation wait for helpers using `browser.wait_for_reload`. | Use the two deadlines from the probe, plus an immediate callback and a disconnected browser. For reload, schedule navigation after network idle and assert the new document was reached. |
| Next / medium | Forward modifier flags for DOM click handlers where Lightpanda supports them. Exercise explicit modal decisions and document the unwrapped default. Scope input changes to observed app behavior. Assigning `.value` plus input/change and typing characters differ for key listeners and user-edit validation. | Assert shift and ctrl in the handler, confirm both branches with Capybara’s dialog wrappers, and compare a key-driven field plus a controlled input in both browsers. |

For older suites, map `driver.cookies`, `network_traffic`, `clear_network_traffic`, `wait_for_reload`, `resize` and `window_handle` to the supported contracts as needed. The old `network_traffic` filters blocked requests differently depending on its argument. Several helpers, including `driver.set_cookie`, `headers=`, `add_headers`, `wait_for_network_idle` and `render`, already exist here. Test the values and side effects before adding aliases. ## 3. Decide which suites still need Chrome

- **URL policies and HTTP auth (larger).** Cuprite 0.20.1 accepts constructor keys `url_blacklist:` / `url_whitelist:` and browser setters under both old and new names. The modern **constructor** spellings are on upstream main and absent from the release. Lightpanda currently consumes none of them. Its native block command has a different pattern language and survives context disposal. Start with a documented pattern subset, reject unrepresentable expressions, and verify allowed and denied requests against a local server. Test two sessions and a reset, including restoration of configured policy. Arbitrary Ruby regexes, interception callbacks and challenge-based `network.authorize` warrant a separate Fetch-domain implementation and tests. [Cuprite browser](https://github.com/rubycdp/cuprite/blob/v0.20.1/lib/capybara/cuprite/browser.rb) · [Constructor change](https://github.com/rubycdp/cuprite/pull/361) · [Lightpanda protocol inventory](.claude/rules/lightpanda-io.md)
- **Raw Ferrum helpers.** Search the adopting suite for `page.driver.browser.page`, `on(:request)`, `console`, `at_css`, `native.node` and rescues naming `Ferrum::` or `Capybara::Cuprite::`. Lightpanda has its own browser, node handles, event payloads and exception classes. A shared method name such as `command` does not establish the same target or return type. Port the specific helper to Capybara or a narrow adapter. Preserve Capybara’s stale-node retry behavior and distinguish JS, selector and transport errors. [Ferrum browser](https://github.com/rubycdp/ferrum/blob/v0.20.1/lib/ferrum/browser.rb) · [Lightpanda errors](lib/capybara/lightpanda/errors.rb) · [Event dispatch](lib/capybara/lightpanda/client/subscriber.rb)
- **Keep a Chrome lane for rendering and multi-window flows.** Lightpanda supports one window, synthetic geometry and a JS-visible viewport. Its scroll helpers are no-ops. A screenshot call can succeed without generating useful visual evidence. Keep actual scrolling, coordinates, CSS hover, image/PDF assertions, multiple tabs, and opener relationships on Cuprite. DOM hover events, HTML5 drag/drop, file upload, iframe scripting and explicitly handled dialogs already have Lightpanda paths. Downloads need their own fixture for an attachment or a download link. A MIME-only navigation has different behavior. [Shared-spec capability list](spec/features/session_spec.rb) · [Specific skipped behaviors](spec/spec_helper.rb) · [Download fixtures](test/features/download_test.rb)

## How to decide when to call it drop-in

Use a small, dev-only differential suite with the same Rack fixtures and helper bodies, run once per registered driver. Start with the table above. Add the registration and two-session reset checks, then migrate an application-owned initializer such as Forem’s while retaining its helper calls. Record any remaining edits to the application specs and any examples assigned to Chrome, with the capability they require. A useful release claim would name the initializer and helper contracts that pass unchanged. Shared Capybara specs alone cannot establish that a suite’s Ferrum calls work.
